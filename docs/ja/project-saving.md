# 保存と復元ポイント

Zoidium は CM3 を取り巻く独立した外部の拡張レイヤーです。プロジェクトファイルは引き続き gzip 圧縮 TAR アーカイブであり、CM3 の `meta`、`project`、およびアセットエントリーを持ちます。任意の `zoidium.json` エントリーは、プロジェクト名と、各エントリーのサイズおよび完全な SHA-256 ダイジェストを追加します。既存の CM3 アセット ID は変更されません。古い Zoidium ビルドは、この追加の整合性メタデータを無視します。

保存は最初に、初期化されていないデフォルトプロパティをシリアル化しないよう、境界付きのオブジェクト/プラグイン初期化を待ちます。次に、接続済みアセットのバイトをページメモリにコピーし、ローカルアセット参照とコンテンツ ID を確認し、アーカイブを構築してから、完成した Blob を Open と同じ検証器でデコードして検証します。フォントとテクスチャのプレビューデコードは、その接続済みバイトの保存には不要です。したがって、保存はビデオエクスポート、プレビューデコーダー、または他のタブのエクスポートワークスペースリースを待ちません。バイトを読み取れない接続済みアセットがあると、保存は停止し、そのアセットを指名します。前のファイルと復元ポイントは引き続き利用できます。エディターですでに不足しているファイル(バイトなしで開かれ、Assets に Missing と表示される)は、After Effects での不足フッテージと同様に、保存を停止しません。そのキーは `zoidium.json` の `missingAssets` に記録され、再開したプロジェクトでは再び不足として表示され、保存後の通知がそれを一覧表示します。プロジェクト内にまったく存在しなくなったアセットへの参照(例えば、画像より長く残ったエディターのみの選択)は、CM3 と同様に保持され、コンソールに 1 回報告されます。保持すべきバイトが存在しないため、保存も Open も妨げません。Zoidium は、保存を成功させるために不足アセットを黙って削除しません。

Browser Save は検証済み Blob のみを書き込みます。File System Access は書き込み可能ストリームを使用し、失敗した書き込みまたはコミットを中止します。Download フォールバックも、ダウンロード開始前に検証します。失敗した保存は、プロジェクトを未保存の状態のままにします。アーカイブ構築中の編集やプロジェクト置換は配信を取り消します。古い保存が、その保存先ハンドルを新しく開いたプロジェクトに接続することはありません。

非同期アーカイブ読み取り、ハッシュ、圧縮、書き込み、および復元ポイントトランザクションの各操作には、10 秒に処理量 4 MB あたり 1 秒を加えた予算があります。ユーザーが開始した保存または Open の手順が予算を超えた場合(低速、ネットワーク、またはクラウドドライブ上の大きなビデオ)、"Still working" の質問が Keep waiting または Stop を提示します。その手順がその間に終了すると自動的に閉じるため、有効なプロジェクトが時間だけを理由に失敗することはありません。自動バックアップと復元ポイントは、質問せずに予算で停止します。Open は、CM3 と同様にオブジェクトの読み込み完了を待ちます。保存も読み込み中のオブジェクトを待ちます。10 秒後、ユーザーは待機継続と今すぐ保存のいずれかを選択します。自動バックアップはその回をスキップします。ピッカーはユーザーの選択を待ちます。ブラウザーのメインスレッドが同期処理でブロックされている間、JavaScript タイマーは実行できません。アーカイブ処理は、非圧縮入力を 2 GB、JSON エントリーを 32 MB、エントリー数を 10,000、プロジェクト入れ子を 128 レベルに制限します。これらの上限を超える入力は明示的に失敗し、現在のプロジェクトはそのまま残ります。

Open、New、Restore、およびプラグイン無効化は最初に、現在のプロジェクトの復元ポイントを保存します。そのバックアップが失敗した場合、例えばブラウザーストレージが満杯の場合、ユーザーは現在のプロジェクトを保持するか、バックアップなしで続行するかを選択します。

復元ポイントの既定間隔は 5 分です。各新しいポイントは、完全な検証済みアーカイブ 1 件とそのメタデータを 1 つの IndexedDB トランザクションに保存します。ライターはそれを読み戻し、サイズと完全な SHA-256 ダイジェストを確認し、回転前にアーカイブを検証します。スナップショット ID は挿入のみで、上書きしません。古い分割レコードは引き続き読み取り可能です。その共有アセットクリーンアップは参照を走査し、両ストアにまたがる 1 つのトランザクションでアセットを削除します。
バックアップ書き込み、検証、クォータクリーンアップ、および回転は、オリジン全体のライターロックを使用します。Web Locks のないブラウザーは、更新可能な IndexedDB リースを使用します。リース所有権は、各変更トランザクション内で確認されます。期限切れまたは置換済みのリースは、ポイントを確定したり保持対象候補を削除したりできません。

自動保持は、各プロジェクトとタブ所有者の最新の検証済みポイントを維持しながら、最近のポイントを保持します。手動ポイントは、削除されるまで保持されます。ストレージが満杯の場合、Zoidium は最も古い追加の自動ポイントを削除して再試行します。最後の検証済みポイントは保持し、空きが依然として不足する場合は報告します。ブラウザーストレージはアプリケーションオリジンにローカルであり、サイトデータを消去すると削除されることがあります。重要なプロジェクトは別途ダウンロードします。

Open と New は、既存プロジェクトを置換する前に検証済み復元ポイントを取得します。Restore は最初に選択したポイントを検証し、次に読み込む前に現在のプロジェクトをバックアップします。失敗すると現在のプロジェクトが残ります。利用できないアセットを含む構造的に読み取り可能なアーカイブは、**Open readable parts** を提示し、不良アセットを一覧表示し、後から再接続できるようその参照を保持します。損傷したプロジェクト文書またはコンテナは部分的に開けません。エラー通知も復元ポイント回復を提示します。

個別およびグループのプラグイン切り替えは、プラグイン無効化の前に検証済みバックアップを取得します。そのバックアップが失敗すると、ユーザーがバックアップなしでの続行を選択しない限り、スイッチは有効のままです。プロジェクトが使用中のプラグインは、プラグインマネージャーの使用ロックを通じて無効化操作も拒否します。シリアル化済みプラグインデータは、その実装が利用できない場合も残ります。Zoidium にはセッション内のプラグイン更新操作がありません。外部コード更新の前に、ダウンロードしたプロジェクトまたは検証済み復元ポイントを用意します。

デスクトップローダーは、この同じ Open パスを使用します。その信頼済みループバック経路は、ファイルを開いた後、通常ファイルの種類とサイズを再度確認します。レンダラー読み取りと読み込みには境界付き待機があり、デスクトップインポートキューを常に解放します。
